# 多应用音量生命周期与写入契约

本次修复覆盖音量入口的对象所有权、系统界面面板的资源释放、滑动期间的音量任务积压，以及后台 Hook 状态广播附带的 Root 检测。共享 UID 播放身份解析继续使用 PR #36 的 `AppVolumePolicy` 与 `AppVolumePlayback`：完整 UID 用于关联播放器，真实包名用于图标，原生 volumeKey 用于读写音量镜像。

## 视图与面板资源

入口的 RingerButtonHelper 放在入口 View 自身的 tag 状态中，原生按钮的展开状态回调按该入口查找 helper。模块不再通过全局表强引用入口与 parent；控制器引用和异步更新使用弱引用。MiSound 的百分比文本仍是宿主视图树的子节点，模块索引仅保留弱引用，轮询回调不强引用卡片和控制器。

每次面板显示使用独立的官方音量列资源组。普通淡出、避让淡出、动画取消、窗口 detach、显示替换均可释放该组，重复回调只释放一次。旧面板的延迟结束不能释放新面板的列。播放探测返回时还检查显示代次和窗口状态，关闭后的过期结果不能重新弹出面板。

普通开关与关闭仍使用原有动画时长和布局计算，高度自动、百分比样式与原生音量列保持同一调用链。

## 音量写入

系统界面、MiSound 各有一个后台消费者。待处理值按完整 UID 合并，同 UID 的连续拖动最多保留一个最新待处理值；正在执行的 IPC 结束后继续处理最新值和其他 UID，不取消松手的最终值。旧的仅包名广播在 MiSound 按包名暂存，随后仍通过包名归属解析完整 UID。

系统界面首先调用 `AppVolumePlayback.applyVolume`。有播放器成功写入时，广播增加 `EXTRA_ALREADY_APPLIED=true`，MiSound 校验包名与 UID 后只调用官方镜像接口，不重复调用音频服务。没有成功写入或直接接口抛异常时，标记为 false，MiSound 保留原来的真实写入兜底。没有该标记的旧广播等同 false。

因此两个目标进程应加载同一模块构建，才能消除双路重复写入。旧 MiSound 进程不识别新标记时仍可调节音量，但会暂时继续重复写入；不以兼容性为代价强制杀进程或整机重启。

原有 `STARTED`、`USAGE_MEDIA` / `STREAM_MUSIC` 筛选、同 UID 全部活跃播放器写入、暂停 / 停止过滤、多用户完整 UID、共享 UID 图标及 volumeKey 兼容不变。音频与包管理 IPC 继续在后台执行。

## Root 检测

Application 冷启动仍初始化配置、状态接收与 LSPosed 服务绑定。Root 检测由首次进入 MainActivity 触发；用户手动点按状态卡片仍可重新检测。页面重建和回到前台不轮询，不把 Root 授权结果写入持久化配置。临时 KernelSU 权限消失后，可手动重新检测。

授权等待上限为 30 秒；拒绝、超时、su 不可用时显示不可用，并清理检测子进程。Hook 状态广播和安全模式启动计数保留原有行为。

## 验证范围

自动回归覆盖共享 UID 与同 UID 多播放器、慢写入时的最终值、不同 UID 的独立更新、旧广播与直接写入失败兜底、取消 / detach 的重复清理、旧资源组和新资源组隔离、Root 拒绝与超时。构建结果以本次交付记录为准，自动测试不能代替真实 ROM 的反射接口和交互验证。

真机验收可由用户手动完成：Apple Music、Bilibili、QQ 音乐、小米音乐分别调节；同 UID 多播放器；入口复用、连续开关、音量条超时收回、窗口重建；高度自动与百分比；打开模块后的 Root 状态与手动重检。所有设备命令、安装和目标进程重新加载遵守 [模块开发工作流](WORKFLOW.md) 的授权边界，临时 Root 下不默认整机重启。
